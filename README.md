# 开发方法论

从实战中积累的分层开发流程框架——让小到修一个按钮、大到做一套系统，每一步都有章可循。

## 概述

本仓库回答一个核心问题：**「怎么确定一次代码改对了？」** 

我们把零散的直觉式修改，整理成一套可重复、可验证、可追溯的结构化流程。每一层有明确入口和出口，每个决策点有检查清单兜底。

## 关键概念

### 分级路径
不是所有改动都走一样重的流程：
- **可执行代码**（PHP/JS/Go/逻辑改动）→ 完整五步法 + 多模型审核
- **鉴权/安全边界改动** → 完整五步法 + 影子双跑（并行新逻辑对比一致率）+ 用例矩阵
- **存量契约变更**（有效期/权限/计费规则等行为变更）→ 完整五步法 + 全量回放（全量存量数据验证零误伤）+ kill switch
- **抢修（生产故障/服务中断）** → 止血优先：先恢复服务（回滚 / 开关 / 降级，当场实测），完整修复放到恢复后（见《四步修改法》「抢修通道」）
- **CSS/纯样式** → 轻量路径：视觉确认（DOM×截图交叉）+ 自适应断点测试，跳过多模型审核
- **文案/配置单值** → 最轻路径：页面确认 + 文件检查

### 验证方法选型（等价 vs 行为变更）
- 语义等价替换（重构/性能优化）→ **影子双跑**：新旧并行，比一致性率（危险信号 = 不一致）
- 行为变更（规则/契约故意改变）→ **全量回放**：一致性指标失效（预期就不一致），比「新规则 ⇄ 预期行为」（危险信号 = 误伤）

### 三回路模型
五步法内部包含三个嵌套的反馈回路：

| 回路 | 速度 | 触发条件 | 作用 |
|---|---|---|---|
| 测↔改（快） | 快 | 测试失败 | 快速红绿反馈 |
| 审↔改（慢） | 慢 | 审核发现 Critical/Major | 代码质量门禁 |
| 改→回归测（中） | 中 | 任何修改 | 保证修复不破坏已有测试 |

### 测试策略三维度
1. **影响面**：改的是什么类型（逻辑/UI/数据库/配置）？
2. **路径枚举**：主路径 + 错误路径 + 边界值 + 并发 + 交互组合 + 回归
3. **正确方法**：每种测试有它「算数」的做法——UI 交互必须用无头浏览器真实点击，curl 模拟 POST 不算

## 设计理念

- **问责重于清晰**：每个改动必须有可追溯的记录——谁改的、为什么改、通过了哪些测试
- **漏测变规则**：每个线上故障都固化为新测试用例或检查清单项，绝不重复踩同坑
- **分层验证**：代码审查不替代测试，测试不替代人工审查——三层全跑
